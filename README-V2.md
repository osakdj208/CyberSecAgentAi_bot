# المرحلة 1 — فحص موقع شامل (dev-v2)

نسخة تطوير منفصلة تماماً عن الإنتاج. لا تُنشر على خدمة فرانكفورت (الإنتاج)
إلا بعد نجاحها على خدمة أوريغون (الاختبار) وموافقة محمد.

## ما أُضيف فوق v0.4

### المحرك (main.py → v0.5.0)
- نقطة جديدة `POST /scans/web` — فحص موقع شامل لكشف فقط، بأربع طبقات:
  1. **سجلات DNS** (A/AAAA/MX/NS/TXT/CAA عبر dnspython).
  2. **فحص HTTP**: الحالة، سلسلة التحويلات، ترويسات الأمان الست
     (HSTS/CSP/X-Frame-Options/X-Content-Type-Options/Referrer-Policy/
     Permissions-Policy) مع درجة، وأعلام الكوكيز (Secure/HttpOnly/SameSite).
  3. **فحص TLS عميق**: الشهادة (المُصدر، الانتهاء، الأيام المتبقية، SANs)،
     إصدار TLS والتعمية، وكشف دعم TLS 1.0/1.1 القديم.
  4. **Nuclei** (v3.3.0 + قوالب v10.5.2): خطورة low–critical فقط، مع
     استبعاد وسوم dos/intrusive/fuzz/brute-force، حد معدل 25، وسقف زمني
     480 ثانية داخل المحرك.
- **تصريح v2 مرتبط بالنطاق**: البوت يوقّع HMAC على {host + مجموعة العناوين
  المحلولة لحظة الاعتماد + kind=web + انتهاء قصير}. المحرك يعيد التحليل
  ويشترط أن تكون عناوينه مجموعة فرعية من الموقّعة (ضد إعادة ربط DNS)،
  وأن تكون كل العناوين عامة عالمية — أي إشارة لعنوان خاص تُرفض.
- `/tools` و`/health` يعرضان حالة Nuclei وDNS بصدق (ready/unavailable).

### البوت (bot.py)
- زر جديد «🌐 فحص موقع شامل»: نطاق ← مرجع تصريح ← إثبات ← طلب معلّق
  (نوعه kind=web) ← اعتماد/رفض الأدمن بالأزرار نفسها.
- عند الاعتماد: يحلّ النطاق، يسكّ التصريح، ينادي المحرك (مهلة 900 ثانية)،
  ويرسل **تقريراً عربياً مفصّلاً مقسّماً** على رسائل متتالية عند الحاجة.
- قاعدة البيانات: عمود `kind` يُضاف بترحيل آمن؛ طلبات IP القديمة لا تتأثر.

### Dockerfile
- يثبّت Nuclei 3.3.0 (إصدار مثبّت) وقوالبه في /opt/nuclei-templates،
  وdnspython في requirements. بقية الصورة كما هي.

## الاختبارات
- 17 اختباراً جديداً (تصريح الويب، حراسة التحليل، تحليل الترويسات،
  محلّل مخرجات Nuclei، تحقق النطاق في البوت، التقرير، تقسيم الرسائل).
- اختبارات v0.4 الأصلية (4 بوت + 13 محرك) تعمل ضد كود v2 دون أي كسر.
- إثبات حي محلي: Nuclei الحقيقي بقوالبه الحقيقية ضد خادم محلي ضعيف
  عمداً، ومخرجاته تمر عبر محلّل المحرك نفسه.

## النشر للاختبار (لاحقاً، بخطوات محسوبة)
1. محمد ينشئ بوت اختبار جديداً من BotFather ويلصق توكنه بنفسه في خدمة
   أوريغون (cyber-agent-us) — خانة TELEGRAM_BOT_TOKEN.
2. تُدفع ملفات dev-v2 إلى فرع `v2-dev` في مستودع CyberSecAgentAi_bot
   وتُوجَّه خدمة أوريغون إلى هذا الفرع عبر API، وتُستأنف.
3. دورة حية كاملة على بوت الاختبار بهدف مصرح (scanme.nmap.org للمحرك،
   وموقع اختبار للويب)، ثم يقرر محمد الترقية للإنتاج أو لا.

## ما ليس في هذه المرحلة
- ZAP الكامل، Trivy، YARA وبقية الكتالوج: ما زالت مخططة، تُبنى مراحل لاحقة.
- لا استغلال ولا هجوم: كل الفحوص كشف وتقارير فقط، خلف بوابة التصريح.

# المرحلة 2 — بحث عميق (v0.6.0 / بوت v3)

إضافات فوق المرحلة 1 دون تغيير أي سلوك قائم؛ وضع «سريع» هو المرحلة 1 كما هي.

- **فحص عميق (اختيار المستخدم بعد الإثبات)**: 
  - قوالب CVE الكاملة تعمل على دفعات سنوية (2025 نزولاً)، كل دفعة بسقف
    200 ثانية وميزانية إجمالية ~900 ثانية، والنتائج تُدمج وتُزال مكرراتها
    وتُعاد إحصاءاتها من القائمة النهائية حتى لا يختلف الملخص عن التفاصيل.
  - **زحف Katana** (عمق 2، نفس النطاق فقط، سقف 150 ثانية) يكتشف الصفحات
    والروابط؛ أبرزها (login/admin/api/swagger...) تُعرض في التقرير، وحتى
    30 رابطاً إضافياً يدخل أهداف فحص القوالب المنتقاة.
  - **اكتشاف أصل الخادم**: نطاقات فرعية من سجلات الشهادات (crt.sh) +
    كلمات معتادة (mail/direct/origin...)، تُصفّى من نطاقات Cloudflare
    المعروفة، ويُتحقق من كل مرشح بطلب مباشر بهوية الموقع.
  - **فحص بجلسة حساب اختبار (اختياري)**: كوكيز جلسة يزوّدها المالك؛
    يعيش في ذاكرة البوت فقط (AUTH_SECRETS) ولا يُكتب في قاعدة البيانات
    أو السجلات أو الردود، ويُحذف لحظة بدء الفحص أو رفض الطلب.
- المحرك v0.6.0، ونقطة /scans/web تقبل deep وauth_cookie ضمن نفس تصريح
  النطاق والعناوين. Dockerfile يثبّت Katana 1.1.0 ويُبقي شجرة cves.
- الاختبارات: 28 اختباراً للنسخة الحالية (منها 11 للمرحلة 2) + 17 أصلية،
  كلها خضراء قبل الدمج.

# المرحلة 2.1 — الأصل المباشر + بصمة المرور (v0.7.0 / بوت v4)

- **فحص خادم الأصل** (زر جديد، نوع طلب origin): المستخدم يعطي الموقع +
  عنوان خادمه الحقيقي، والتصريح HMAC مرتبط بالزوج (موقع + عنوان أصل).
  المحرك يقيس طبقات الويب من الأصل نفسه: HTTP بطلب خام أحادي القفزة
  بهوية Host/SNI للموقع (التحويلات تُسجَّل ولا تُتَّبع)، TLS على الأصل،
  وNuclei موجّهاً لعناوين الأصل مع ترويسة Host. الزحف لا يعمل في هذا
  الوضع بتصميمه.
- **بصمة مرور متفق عليها**: ترويسة سرية (اسم: قيمة) يزوّدها المالك بعد
  أن يضيف قاعدة سماح لها في جدار حمايته (Cloudflare WAF)، فتمرّ طلبات
  الفحص (المسبار + Katana + Nuclei) من الباب الرسمي. تعيش في ذاكرة
  البوت فقط (PASS_SECRETS) مثل جلسة الاختبار، ولا تُحفظ ولا تُعاد في
  أي رد — المحرك يبلّغ pass_used فقط.
- الاختبارات: 45 اختباراً للنسخة الحالية (17 منها للمرحلتين 2 و2.1)
  + 17 أصلية، كلها خضراء قبل الدمج.

# إضافة و٨ — بطاقة حساب تيليجرام (بوت v4.1)

- زر جديد «🪪 بطاقة حساب تيليجرام» في القائمة الرئيسية: المستخدم يرسل
  @username أو رابط t.me أو معرفاً رقمياً، فيعرض البوت بطاقة بيانات
  عامة فقط: الاسم، النوع (مستخدم/بوت/قناة/مجموعة)، عدد الأعضاء أو
  المشتركين، الوصف العام، وتقدير تقريبي لفترة إنشاء الحساب مستنتج من
  نطاق المعرف الرقمي (تيليجرام لا ينشر التاريخ الحقيقي، والبطاقة تصرّح
  أنه تقدير).
- المصادر: الصفحة العامة t.me/<username> + Bot API ‏(getChat /
  getChatMemberCount) للقنوات والمجموعات العامة. لا بوابة اعتماد لهذه
  الأداة لأنها لا تفحص هدفاً — بيانات منشورة علناً فقط، ولا تُجمع أي
  بيانات خاصة.
- التنفيذ في البوت فقط (bot.py) دون تغيير المحرك. الاختبارات: 63
  اختباراً للنسخة الحالية (18 جديدة لهذه الإضافة) + الأصلية، كلها خضراء.

# إضافة و٨ العميقة — بحث MTProto (بوت v4.2)

- وحدة جديدة tgdeep.py: عميل Telethon بجلسة StringSession لحساب تيليجرام
  مخصص، يحلّ أي @username عام إلى ما لا تكشفه واجهة البوتات: الرقم
  الرقمي، علامات تيليجرام الرسمية (verified/scam/fake)، عدد صور الملف،
  النص الكامل للوصف، عدد مشتركي القناة ومجموعة النقاش المرتبطة بها.
  بيانات عامة فقط — أرقام الهواتف لا تُقرأ ولا تُعاد أبداً.
- التفعيل بمتغيرات بيئة فقط (TG_API_ID / TG_API_HASH / TG_SESSION)؛
  بغيابها تبقى البطاقة العامة كما هي دون أي تغيير سلوكي. الجلسة سر كامل
  الصلاحية: تُقرأ من البيئة فقط ولا تُسجَّل ولا تُطبع.
- أمان من الحظر: البحث متسلسل ومُباعَد (3 ثوانٍ على الأقل بين كل
  بحثين) بقفل واحد، وأي خطأ (حظر مؤقت، جلسة منتهية) يُبلَّغ داخل البطاقة
  ويُكمل بالبطاقة العامة.
- أُصلح أيضاً سطر «إحصائية عامة» الزائد في بطاقات المستخدمين (لا يظهر
  إلا مع أرقام مشتركين/أعضاء فعلية).
- الاختبارات: 71 اختباراً للنسخة الحالية (8 جديدة للعمق) + الأصلية،
  كلها خضراء قبل الدمج.

# إضافة ر١+ر٣ — بطاقة رقم هاتف (بوت v4.3)

- زر جديد «📱 بطاقة رقم هاتف»: المستخدم يرسل رقماً بالصيغة الدولية،
  فيعرض البوت بطاقة فورية بلا بوابة اعتماد (بيانات عامة فقط).
- ر١ (بيانات الترقيم): مكتبة phonenumbers (بيانات libphonenumber
  العالمية) — الدولة (بأسماء عربية)، المشغّل المسجل لنطاق الرقم مع

  حذفها فوراً؛ تيليجرام لا يعيد إلا من سمح مالكه بـ«العثور عليّ
  برقمي»، فيُعرض ملفه العام (معرف/اسم/رقم رقمي/علامات رسمية) أو
  «لا حساب قابل للاكتشاف». واتساب وسيغنال: تحققنا فعلياً أن صفحة
  واتساب العامة متطابقة للمسجل وغير المسجل، فتقرر البطاقة بصدق أنه
  لا تحقق عاماً موثوقاً لهما بدل اختلاق نتيجة.
- تحقق حي قبل النشر: استيراد رقم حساب البحث أعاد ملفه العام الصحيح،
  ورقم وهمي أعاد «غير موجود»، وبطاقات الترقيم لأرقام يمنية وبريطانية
  وأمريكية صحيحة الدولة والمشغّل والنوع.
- الاختبارات: 88 اختباراً (13 جديدة) + الأصلية، كلها خضراء قبل الدمج.

# التقييم الشامل للمنظومة EASM (محرك v0.8.0 / بوت v5)

- زر جديد «🏢 تقييم شامل لمنظومة»: تدفق نطاق ← مرجع تصريح ← إثبات ←

  ومجموعة عناوينه (نفس مخطط web).
- المحرك POST /scans/full: اكتشاف ساكن للنطاقات الفرعية (شهادات

  «متخطّى» ولا يُسقط بصمت.
- تدقيق أمان البريد من DNS العام فقط: SPF (موجود؟ قوة الإنهاء)،

- درجة أمان 0-100 شفافة: سقوف لكل فئة (Nuclei 40، منافذ 24، بريد
  22، TLS 16، ترويسات 12) وكل خصم يُدرج سببه في التقرير، مع قائمة
  أولويات إصلاح مرتبة.
- الاختبارات: 109 اختبارات (21 جديدة: تصريح full وتوافقه بين البوت
  والمحرك، تدقيق البريد بمحلل DNS وهمي، حساب الدرجة وسقوفها،

  + الأصلية، كلها خضراء قبل الدمج.

# الفحص الموحّد — المرحلة أ: الأساس الموحّد (بوت v6)

- زر جديد «🧩 فحص موحّد (موقع + تطبيق)»: طلب واحد يجمع نطاقاً
  (إلزامي) + رابط متجر اختيارياً + ملف APK أو رابطه المباشر
  اختيارياً، ثم مرجع تصريح وإثبات واعتماد أدمن واحد — نوع طلب
  kind=unified، وعمودان جديدان store_link وapk_ref (JSON) بهجرة
  تلقائية بنفس نمط الأعمدة السابقة.
- عند الاعتماد: يُشغَّل التقييم الشامل للمنظومة كما هو (نفس تصريح
  full ونفس نقطة المحرك /scans/full — لا تغيير في المحرك)، وتُجلب
  بطاقة التطبيق العامة من صفحة المتجر (Google Play / App Store)
  عبر وسوم Open Graph، ويُضمّ مرجع ملف التطبيق المستلم.
- التقرير موحّد: بطاقة المتجر + قسم المرفق + تقرير التقييم الشامل
  كاملاً + ملاحظة صريحة أن الدرجة الحالية درجة المنظومة وأن درجة
  التطبيق تنضم في المرحلة ب (محرك تحليل APK الثابت).
- درس تقني موثق بالتجربة: صفحات Google Play حجمها ~1.3MB وتضع
  وسوم og: قرب نهايتها (بايت ~1.04M) — سقف قراءة 512KB كان يعيد
  بطاقة فارغة بصمت؛ رُفع السقف إلى 2MB.
- تحقق حي قبل النشر: بطاقتا Telegram من المتجرين حقيقيتان
  (الاسم بعد تنظيف لاحقة المتجر والوصف المنشور).
- الاختبارات: 119 اختباراً (10 جديدة للموحّد) + الأصلية، خضراء.

# الفحص الموحّد — المرحلة ب: محرك تحليل التطبيقات (محرك v0.9.0 / بوت v7)

- المحرك POST /scans/apk: يستقبل بايتات APK خاماً (حتى 80MB) ولا
  ينفّذ إلا بتصريح HMAC من نوع apk مرتبط ببصمة SHA-256 للملف نفسه —
  يعيد المحرك حساب البصمة من البايتات المستلمة ويطابقها، فلا يمكن
  إعادة استخدام اعتماد على ملف آخر.
- التحليل (androguard 4.1.4، خفيف: فئة APK + مسح سلاسل DEX يدوياً
  دون تحليل DEX الكامل): الهوية والإصدارات وSDK، الصلاحيات مع
  تصنيف الخطيرة، المكوّنات والمكشوف منها بلا حماية (مسح DOM
  للمانيفست بقواعد exported الافتراضية)، أعلام debuggable /
  allowBackup / usesCleartextTraffic / إعدادات الشبكة، أنماط أسرار
  مدمجة (9 أنماط: مفاتيح AWS/Google/GitHub/Stripe/Slack ومفاتيح
  خاصة وJWT وFirebase وتعيينات عامة — تُعرض بأول 6 أحرف فقط)،
  روابط URL والنطاقات وروابط HTTP الواضحة، مكتبات معروفة من
  أسماء الحزم، وشهادة التوقيع (الجهة والانتهاء والبصمة وذاتية
  التوقيع).
- درجة تطبيق 0-100 بسقوف فئات معلنة (إعدادات 39، أسرار 20،
  مكوّنات 16، منصة 14، صلاحيات 12) وكل خصم مسبّب.
- البوت: ينزّل الملف (من تيليجرام بسقف 21MB أو من الرابط المباشر
  بسقف 60MB)، يحسب بصمته، يصكّ التصريح، ويرفع البايتات للمحرك.
  التقرير الموحّد يعرض قسم التطبيق كاملاً ودرجة موحّدة =
  ٦٠٪ منظومة + ٤٠٪ تطبيق عند اكتمال التحليلين، وفشل التحليل
  يُبلَّغ صراحة بسببِه.
- تحقق محلي قبل النشر على تطبيق حقيقي (Binary Eye من F-Droid):
  تحليل كامل في ~0.5 ثانية — 12 صلاحية (3 خطيرة)، 8 مكوّنات
  مكشوفة، allowBackup وcleartext مفعّلان، شهادة F-Droid تنتهي
  2046، درجة 64.
- دروس موثقة: (1) asn1crypto هنا يعرض not_valid_after لا
  not_valid_after_utc — يُقرأ بالبديلين. (2) get_attribute_value
  في androguard 4.1.4 لا يصلح لقراءة exported للمكوّنات — مسح
  DOM عبر get_android_manifest_xml (عنصر lxml) هو الطريق الموثوق.
- الاختبارات: 137 اختباراً (18 جديدة) + الأصلية، خضراء قبل الدمج.

البنود الجديدة تعمل داخل التقييم الشامل والموحّد (نفس التصريح ونفس
التقرير) دون أي تغيير في التدفقات القائمة:

- كشف الاستيلاء على النطاقات الفرعية: سلسلة CNAME لكل اسم مكتشف
  (حتى 20) تُطابَق مع 14 خدمة معروفة ببصمات صفحاتها «غير المُدّعاة»
  (GitHub Pages، Heroku، S3، Azure، Shopify، Ghost، Surge،
  Bitbucket، Fastly، Pantheon، Netlify، GitLab Pages،
  WordPress.com). الحكم موسوم بقوة دليله: «مؤكد» حين تجيب صفحة
  الخدمة نفسها ببصمة عدم الادعاء، و«محتمل» حين لا يعود الهدف يُحلّ
  إطلاقاً. الاسم الذي يجيب طبيعياً مستخدَم ولا يُبلَّغ أبداً.
- تدقيق DNS العميق: محاولة نقل منطقة (AXFR) محدودة من خوادم أسماء
  النطاق نفسه فقط (حتى 3)، حالة توقيع DNSSEC (DS/DNSKEY)، وسجلات
  CAA مع نصوصها.
- الدرجة: فئتان جديدتان بسقوف معلنة (استيلاء 20: مؤكد −12 ومحتمل
  −6، وDNS ‏12: ‏AXFR مفتوح −10 وغياب CAA ‏−2). غياب DNSSEC ملاحظة
  بلا خصم.
- الاختبارات: 154 اختباراً (17 جديدة) + 13 أصلية، خضراء قبل النشر.
- ملاحظة تحقق: محلّل DNS في هذه الآلة الافتراضية معترَض ولا يعيد
  سجلات NS — المنطق مُثبت بالاختبارات، والإثبات الحي من داخل البوت
  على Render كالمعتاد في كل المراحل.

## المرحلة ج٢ — فحص API/GraphQL + تعدين JavaScript (محرك v0.11.0)

داخل التقييم الشامل/الموحّد، لكل مضيف حي (حتى 3، ضمن ميزانية الوقت):

- فحص سطح API: خمسة مسارات لوثائق OpenAPI/Swagger (تُقبل فقط إن
  احتوى JSON على مفتاح openapi/swagger فعلي — مع عنوان الوثيقة وعدد
  نقاط النهاية المعلنة)، ثلاث صفحات وثائق (Swagger UI / Redoc)،
  ومسارا GraphQL بسؤال الاستبطان الأدنى فقط
  {__schema{queryType{name}}} — إثبات أن الاستبطان مفعّل دون سحب
  المخطط الكامل ودون لمس أي نقطة أعمال.
- تعدين JavaScript: ملفات نفس المضيف فقط (حتى 8، بسقوف حجم) تُفحص
  بأنماط الأسرار التسعة نفسها الخاصة بمحرك APK (تُعرض بأول 6 أحرف
  فقط)، وتُستخرج مسارات API وعناوين IP الداخلية والنطاقات الخارجية
  المشار إليها.
- الدرجة: فئة «surface» بسقف 16 (سرّ في JS ‏−8، استبطان GraphQL
  ‏−5، عناوين داخلية −3، وثائق API مكشوفة −2).
- الاختبارات: 167 اختباراً (13 جديدة) + الأصلية، خضراء قبل النشر.
  درس اختبار: موجّه الطلبات الوهمي بـ endswith جعل "/graphql"
  يطابق "/api/graphql" — خُصّصت المفاتيح بعناوين كاملة.
